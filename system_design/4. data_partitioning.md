# Data Partitioning
Data Partitioning is a process of dividing a large database into smaller, more manageable parts called patritions or shards.

## 1. Patritioning Methods

### Horizontal Partitioning
- divides a database table into multiple partitions or shards, with each partition containing a subset of rows.
- each shard is typically assigned to a different database server, which allows for parallel processing ans faster query execution times.
- Key problem: if the value whose range is used for partitioning isn't choosen carefully, then the partitioning scheme will lead to unbalanced servers.

### Vertical Partitioning
- splits database table into multiple partitions of shards, with each partition contains a subset of columns.
- can help optimize performance by reducing the amount of data that needs to be scanned, especially when certain columns are accessed more frequently than others.
- Example: e-commerce website stores customer data in a database table. Can partition the customer table based on the type of data, so that personal information such as name and email are stored in one shard, while order history and payment information are stored in another shard.

### Hybrid Partitioning
-combines horizontal and vertical partitioning.

## 2. Partitioning Criteria
- factors or charecteristics if data that can be used to divide a large dataset into smaller parts or partitions.

### Key or Hash-Based Partitioning
- apply a hash function to some key attributes of the entitiy we are storing. That tuelds the partition number.
- Example: 100 db servers, ID is numeric. The hash function is "ID % 100" (modulo). This will give us the server number to store/read that record.
- Fundamental Problem: it effectively fixes the total number of DB servers, since adding new servers means changing the hash function which would require redistribution of data and downtime for the service.
- Workaround: Consistent hashing is a method of distributing keys across servers using a hash ring, where adding or removing a server only redistributes a small portion of the keys. Keys and servers are assigned positions on the ring, and each key is stored on the first server found clockwise from its position.

### List partitioning
- each partition is assigned a list of values, so whenever we want to insert a new record, we will see which partition contains our key and then store it there.
- Example: all users living in: Iceland, Norway, Sweden, Finland, Denmark will be stored in a partition for the Nordic countries.

### Round-robin partitioning
- uniform (равномерное) distribution. With "n" partitions, the "i" tuple is assigned to partition (i mod n). (where i is a sequence number)

### Composite Partitioning
- combine any of the above partitioning schemes to devise a new scheme.
- for example: first applying a list partitioning schme and then a hash-based partitioning.

## 3. Common Problems of Data Partitioning

### Joins and Denormalization
- once database is partitioned and spread across miltiple machines it is often not feasible to perform joins that span database partitions. Such joins will not be prefomance efficient since data has to be compiled from the multiple servers.
- Workaround: denormalize the database, so the queries that previously required joins can be performes from a single table. (need to deal with data insonsistency)

### Referential integrity
- it's difficult to enforece data integrity constraints such as foreign keys
- most RDBMS do not support fk key constraints, it's enforces with application code. Applications have to run regular SQL jobs to clean up dangling (missing) references.

### Rebalancing (change partition scheme)
- Because data distiribution is not uniform (somewhere a lot, somewhere a bit). e.g. lot of places (cities, vilages, districts) for a particular ZIP (e.g. 06300, 06100 ... ) code that can't fit into one database partition.
- There is a lot of load on a partition. e.g. too many requests handled by the DB partition dedicated to user photos.


In such cases we have to create more DB partitions or have to rebalance existing partitions, which means the partition scheme is changed and all existing data moved to the new locations. Without incurring downtime it's extremely difficult. Using scheme like directoty-based prtitioning make rebalancing easier but there is less relabitlity (creating a new single point of failure (i.e. the lookup service/database)")
