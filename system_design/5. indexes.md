# Indexes

The goal of index - make faster to search.

Indexes speed up reading but make slow to write/update/delete.

## Types of indexes

### Btree (Balanced Tree)
- the most popular (PostgreSQL, MySQL, Oracle)
- good for equality, range, sort ( =, <, >, BETWEEN, ORDER BY)
- data is storing in sortered way that allows search fast

### Hash
- perfect for equal match '='
- do NOT support range search 'BETWEEN', '<', '>'
- PostgreSQL supports hash indexes but they are not popular cause of constraints

### Bitmap
- Uses bitmaps to represent column values
- Very efficient for columns with small number of distinct values (e.g. gender, status, visibility)
- Often used in analytical databases (data warehouses)

### Compostite / Multi-columns index (составной индекс)
- An index on multiple column
- Useful for queries that filter or sort by several columns
- Note (!): column order in index matters. If index is [customer_id, status, created_at DESC], that is good for search by "customer_id", "customer_id + status", "customer_id + status + ORDER BY created_at DESC", but that wouldn't work with "status" only or with "ORDER BY created_at DESC"

### Unique index
- Ensures uniqueness of a column or a set of columns
- Also serves as an index to speed up lookups

### Partial /Liltered index
- Created only for a subset of rows matching a condition "where"
- Saves space and speeds up queries that match the filter condition
- Useful for exact filter match
- Example:
```
    CREATE INDEX idx_orders_shipped
    ON orders(created_at DESC)
    WHERE status = 'shipped';
```

This index contains only "status = 'shipped'". That allows to save space (no need to save all other statuses like pending or delivered)

### Full-text index
- For text search (e.g. LIKE '%word%' or advanced document search)
- Implements structures like an invertered index
- Example

Table:

| id | title            | body                      |
| -- | ---------------- | ------------------------- |
| 1  | Databases 101    | Introduction to databases |
| 2  | Performance Tips | Database performance tips |
| 3  | Learning SQL     | SQL basics and database   |

Usual B-Tree index:

title -> row_ids
Databases 101      -> 1
Learning SQL       -> 3
Performance Tips   -> 2

- good for exact match of the word
- do not help by finding by phrase

Inverted index:

database   -> 1,2,3
databases  -> 1
introduction -> 1
performance -> 2
tips        -> 2
sql         -> 3
learning    -> 3
basics      -> 3

To find "database & performance" need to do:
- database -> 1,2,3
- performance -> 2
- intersect [1,2,3] and [2] => result is 2

### Spatial(пространственные) / GiST / GIN / BRIN
PostgreSQL-specific examples:
- GiST - generalized search tree for various data types (geometry, ranges)
- GIN - for arrays, JSON, full-text search
- BRIN(Block Range Index) - very compact index for large tables with ordered values (e.g.dates)

BRIN Example:

```
CREATE TABLE event_logs (
    id BIGSERIAL PRIMARY KEY,
    event_time TIMESTAMP NOT NULL,
    event_type TEXT,
    message TEXT
);
```

- We have a events log with billions log ordered by event_time (it's important to be ordered)

```
CREATE INDEX idx_event_logs_time
ON event_logs USING BRIN(event_time);
```

- The table is split into data blocks (usually 8KB each)
- For each block, the index stores the minimum and maximum value of the column:
```
Block 1: min = '2025-01-01 00:00', max = '2025-01-01 00:59'
Block 2: min = '2025-01-01 01:00', max = '2025-01-01 01:59'
Block 3: min = '2025-01-01 02:00', max = '2025-01-01 02:59'
...

```
- When querying, for example: `WHERE event_time >= '2025-01-01 01:30' AND event_time < '2025-01-01 02:00';`
PostgreSQL skips blocks that don't match the range (!), checking only the min/max for each block.

Advantages of BRIN:
- Very small index size, almost not storage overhead.
- Perfect for very large tables with ordered data (!)
- Fast for range queries

Disadvantages
- not efficeient for scattered (not ordered) values or frequent point queries (example `SELECT * FROM event_logs WHERE event_time = '2025-01-01 01:17';` for this it's better to use B-Tree)
- works best when data is mostly sortered on the indexed column
