# SQL vs NoSQL

2 main types of solutions: SQL and NoSQL

## SQL
Store data in rows and columns
Popular databases: MySQL, Oracle, SQLite, Postgres, MariaDB

## NoSQL

### Key-Values Stores
- Data stored in an array key-value pairs
- key -> unique string/id; value -> an opaque (не прозрачный) block of data (bytes, string, JSON)
- The database does not understand the structure of the value; it’s a “black box.”
- Operations: get value by key, set value by key, delete. That's it.
- Perfect for caching, sessions and fast lookup operations.
- Popular dbs: Redis, Dynamo

### Document Databases
- Data stored in documents and these document are grouped in collections
- A document can be indexed by nested fields, queried and aggregated
- The document "sees" the internal source of the document


### Wide-Column Databases
- Instead of "tables" -> column families which are containers for rows.
- Don't need to know all the columns up front and each row doesn't have to have the same number of columns
- Columnar dbs are best suited for analyzing large datasets. (logs, sensors, analytics BigData)
- Popular dbs: Cassandra, HBase

Example:

```
Column Family: Users
RowKey: user_id

Row 1: { name: "Alice", email: "alice@example.com" }
Row 2: { name: "Bob", email: "bob@example.com", phone: "12345" }
```

- A row is identified by a key "user_id"
- Different rows can have different sets of columns
- Data is physically stored by columns rather by rows ->  enabling fast access to large datasets across specific columns

### Graph Databases
- Store data whose relations are best represented in a graph
- Stores data in graph structures with noeds (entities), properties (information about the entities), and lines (connections between the entities)
- Popular dbs: Neo4J, InfiniteGraph



## Hihg level differences between SQL and NoSQL

Storage: SQL stores data in tables. NoSQL have different data storeage models (key-value, document, graph, columnar)

Schema: In SQL fixed schema. In NoSQL schema is dynamic (columns can be added on the fly and each "row" doesn't have to contain data for each "column")

Querying:  SQL databases use SQL (structured query language) for defining and manipulating data, which is very powerful. In NoSQL queries are focused on collections of documents or key-value pairs. The queries are centered on searching and filtering documents within a collections rather than joing tables. Fast access to individual documents but the capabilities for complex aggregations and joins are more limited compared to SQL

Scalability: In most common situations SQL databases are vertically scalable (add memory, cpu etc.) which can get very expensive. It's possible to scale a relational db across multuple servers but this is a challenging and time-consuming process.
NoSQL are horizontally scalable (can add more servers easil) Cheap commodity hardware or cloud instances can host NoSQL dbs. A lot of NoSQL technologies are also distribute data across servers automatically.

Reliability or ACID Compliancy (Atomicity, Consistency, Isolation, Durability): The most of relational dbs are ACID compliant. SQL dbs are better.
Most of the NoSQL solutions sacrifice (жертвуют) ACID compliance for performance and scalability.

## Reason to use SQL database
- Need to ensure ACID compliance. IT reduces animalies and prorects the integrity of dbs by prescribing exactly how transactions interact with the database.
- Data is structured and unchanging. If business is not experiencing massive growth that would requie more servers.

## Reason to use NoSQL database
- Storing large volumes of the data (1-2 terabytes and more) that have little or no structure
- Cloud based dtorage is an excellent cost-saving solution but requires data to be easily spread across multiple servers to scale up.
- Rapid development. If you're working on quick iterations of the system which require making frequent updates to hte data structure without a lot of downtime between version, a relational database will slow you down.

## ACID Compliance (соответствие принципам ACID)
ACID Compliance is a set of properties that ensure reliability and predictability of transactions in a database.
Therm is used often for relational databases but can apply to other systams that support transactions.

1) Atomicity - a transaction is executed fully or not at all. If something goes wrong, all changes are rolled back
2) Consistency - the database always remains in a valid state, respecting all constraints (e.g uniqueness, data types, fk keys)
3) Isolation - concurrently running transactions do not interfere with each other; each sees the db as if it were the only one running.
4) Durability - once transaction is committed, the data is preserved even in case of a system failure
