# Bloom filters

Bloom filter is a space-efficient probabilistic data structure for set membership tests - it can quickly tell you if an item is definitely not in a set or if it is probably in the set.

- false negatives are impossible
- false positives are possible

## What Exactly Is a Bloom Filter?

2 main components:
- Bit Array: An array of bits (0s and 1s), initially all set to 0
- Hash Functions: Several independent hash functions that each take an input item and produce an index (a position in the bit array)

When you add an item to a Bloom filter -> item is run through each of the hash functions to get multiple array positions -> bits at all those positions are set to 1

To query an item (check membership), you run it through the same has functions to get those positions and check the bits:
- if any one of those bits is 0 -> the item was definitevely never added (definitely not in the set)
- if all of those bits are 1 -> item is probably in the set. (could be a false positive)

### Why use multiple hash functions?
- each hash function giving the item a few independent "labels" or positions in the bit array
- this redudancy makes false negatives impossible
- if too many items crowd the same few positions -> can collectively cause false positives (by filling in all labels for some item that wasn't actually added)

## How Bloom Filters Work (Step by Step)

1) Initialize: Start with a bit array of length N, all bits set to 0. Decide on k independent functions (each should output a number in the range 0 to N-1)

2) Adding an Item: feet an item into kach of the k hash functions to get k array indices. For each index -> set the bit at that position in the array to 1. (if bit is already 1 -> leave it as 1). After adding many times, some bits in the array will remain 0, and some will be 1.

3) Querying an Item: run the element through the same k hash functions to get k positions. Then check those positions in the bit array:
- if any is 0 -> definitely not in the set
- if all k bits are 1 -> "possibly in the set"

4) Dealing with False Positives: if the Bloom filter returns "probalby in set", one usually double-checks via a slower method (e.g. doing the full lookup in a database cache) if exact confirmation is needed. The Bloom filter's job is mainly to **screen out fefinitively missing items quickly**, to avoid wasting time on costly lookups for items that aren't there.

These steps make Bloom filter extremely fast and memory=efficient. O(k) - a constant. In practice k is fixed and usually small (like 3 or 10)

Standard Bloom filter does not support removals. Once a bit is set to 1, clearing it could remove information about other items that hashed to that bit. (There are variants like counting Bloom filters but htat use more memory and complexity). For the basic Bloom filter, you can only add items (or reset everything)


## Understanding False Positives (Why "Probably?")

It's because different items **overlap** in the bits they set.

### Controlling the false positive rate:
The probability of a false positive can be turned by adjusting the size of the bit array and the number of hash functions. Larger bit array -> bits are more sparcely filled for the same number of items, reducing the chance of accidental overlaps.

More hash functions mean each item covers more bits. Which can either increase or decrease false positives depending on balance - too few hashes and each item doesn't mark enough territory (for ex. if k = 1 => item A and item B could return the same number which is false positive), too many -> you fill the array too quickly.

In practical terms, designers choose parameters so that false positive probability is very low (say 1% or 0.1% or even less) based on what's acceptable for the application.

Trade-off: more memory = fewer lalse positives.

False positives are the price we pay for massive space and time savings. In exchange for never missing an actual member and using very little memory, we accept a slim chance of fetting a "maybe" for something that isn't really there.
