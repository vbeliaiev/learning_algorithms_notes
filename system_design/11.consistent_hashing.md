# Consistent Hashing

## Background

Data partitioning - process of distributing data across a set of servers. It improves scalability and performance of the system.

Data replication - process of making multiple copies of data and storing them on different servers. It improves the availability and durability of the data across the system.

## What is data partitioning?

The act of distributing data across a set of nodes is called data partitioning.

Two challenges when we try to distribute data:
1) How do we know which node a particular piece of data will be stored?
2) When we add or remove nodes, how do we know what data will be moved from existing nodes to the new nodes? How can we minimize data movement when nodes join or leave?

Native approach:
- use suitable hash function to map the data key to a number -> find a server applying modulo on this number and the total number of servers.
- Problem: when we add or remove a server, all our existing mappings will be broken. This is because the total nb of servers will bechanges, which was used to find the actual server storing the data. To fix it we have to remap all keys and move our data based on the new server count, which will be a complete mess!

### Consistent Hashing to the rescue

Consistent Hashing maps data to physical nodes and ensures that only a small set of keys move when servers are added or removed.

Consistent Hashing stores the data managed by a distributed system in a ring. Each node in the ring is assigned a range of data.
The start of the range is called a token. This means that each node will be assigned one roken. The range assigned to each node is computed as follows:

Range start: Token value
Range end: Next token value - 1

Here are examples of tokens and data ranges of the 4 nodes:

{ server: "Server 1", token: "1", range_start: "1", range_end: "15" },
{ server: "Server 2", token: "26", range_start: "26", range_end: "50" },
{ server: "Server 3", token: "51", range_start: "51", range_end: "75" },
{ server: "Server 4", token: "76", range_start: "76", range_end: "100" }

When the system needs to read or write data:
- the first step it performs is to apply the MD5 hashing algorithm to the key.
- the output of the hashing lgorithm determines within which range dhe data lies -> on which node the data will be stored
So, the hash generated from the key tells us the node where the data will be stored

The Consistentt Hashing scheme works great when a node is added or removed from the ring. In this case only next node is affected. Example: When a node is removed, next nodes becomes responsible for all of the keys sored on the outgoing node.

Problem: This scheme can result in non-uniform data and load distribution.

## Virtual nodes

Potential issues associated with a manual and fixed division of the ranges:
- Adding or removing nodes: Will result in recomputing the tokens causing a significant administrative overhead for large cluster
- Hotspots: Since each node is assigned one large range, if the data is not evenly distributed, some nodes can become hotspots
- Node rebuilding: Sonce each node's data might be replaced (for fault-tolerance) on a fixed number or other nodes, when we need to rebuild a note, only it's replica nodes can provide data. This puts a lot of pressure on the replica nodes and can lead to service degradation.

Solution:
Instead of assigning a single token to a node, the hash range is divided into multiple smaller ranges, and each physical node is assigned several of these smaller ranges. Each of these subranges is considered a Vnode.
With Vnodes, instead of a node being responsible for just one token, it's responsible for many tokens (or subranges)

### Advantages of Vnodes

1) Vnodes help spread the load more evenly across the physial nodes on the cluster by dividing the hash ranges into smaller subranges -> speed up the rebalancing process after adding or removing nodes.
2) Make it easer to maintain a cluster containing machines of different types. We can assign a hight number of sub-ranges to a powerful server and a lower number to less powerful server
3) Decreases the probability of hotspots since Vnodes help assign smaller ranges to each physical node


## Data replication using Consistent Hashing

> The replication factore is the nb of nodes that will receive a copy of the same data. Example: if replication factor is 2 -> meanst there are 2 copies of each data item, where each copy is stored on a different node.

Each key is assigned to a coordinator node, which first stores the data locally and then replicaties it to the following nodes on the ring.

In eventually consistent system, this replication is done asyncronously. (in background) It's used to achieve high availability.

## Consistent Hashing in System Design Interviwes
Consistent Hashing helps with efficiently partitioning and replicating data, so any distributed system that needs to scale up or down or wants to achieve high availability through data replication can use Consistent Hashing.
Examples:
- any system working with a set of storage (or database) servers and needs to scale up or down based on the usage(ex.: the system might need more storage during Christmas because of high traffic)
- any distributed system that needs dynamic adjustment of its cache usage  by adding or removing cache servers based on the traffic load
- any systam that wantts to replicate its data shards to achieve high availability

Consistent Hashing use cases: AWS Dynamo and Apache Cassandra
