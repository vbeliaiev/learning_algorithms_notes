# Strong vs Eventual Consistency

Strong consistency - any read of data will return the most resent write. Write operation is propagated to all replicas before it is considered successful.
Trade-offs of Strong Consistency is latency and availability. Because a write must be confirmed by multiple nodes, typically takes logner to complete. Sacrifices some performence and potentially availability for the sake of accuracy.


Eventual consistency - if no new updates are made to a piece of data -> all copies of that data will eventually become consistent (the same).
When write in one node -> the node will apply the update, and then propagate the change to other nodes in the background. Won't wait for all the others to acknoweledge the update before reporting success to the client.
- Risk of returning stale data.
- Performance is typically much better.

Strong Consistency:
- Every read gets the latest write (no stale data)
- Higer latency
- Reduced availability
- Strong consistency level. (all or nothing)
- Use Cases: Where accuracy is paramount: Financial transactions, banking systems, booking systems

Eventual Consistency
- Reads might be stale. Data updates propagates over the time
- Lower latency
- Hihg availability
- Weak (eventually strong) consistency level
- Use Cases: High-volume or globally distributed systems. Social media feeds, messaging apps, analytics data. Often use NoSQL dbs

# Latency vs Throughput

Latency measures delay - how long it takes for a single request to be processed from start to finish. Measured in units of time (milliseconds, seconds). Lower latency - more responsive system.
- Focus on delay or time, focusing on speed
- High latency is not good for user experience
- improve throughput could result higer latency

Throughput - amount of data transferred over a tetwork or processed by a system in a given amount of time. Measured in units of data per time. (Mbps - Megabits per second). Higer throughput indicates a higher data processing capacity.
- about the volume of work or data, focusing on capacity
- low throughput - slow data transfer rates.
- improve latency could reult lower throughput

To improve latency:
- Optimize Network Routes: Content Delivery Networks.
- Caching Frequently Accessed Data
- Upgrade Hardware
- Use Faster Communication Protocols: e.g. HTTP/2
- Database Optimization: Indexing, optimized queries.
- Load Balancing
- Code Optimization
- Minimize External Calls

To improve throughput:
- Scale horizontally (add more servers)
- Implement Caching
- Parallel Processing
- Batch Processing
- Optimize Database Performance
- Asynchronous Processing
- Network Bandwidth

# ACID vs BASE Properties in Databases

- ACID is about keeping transactions strictly correct and reliable
- BASE - keeping the system basically available and scalable (even if data might be briefly inconsistent)

ACID:
- A = Atomicity -> Each transaction is either fully completed or not executed at all
- C = Consistency -> Each transaction brings the database from one valid state to other
- I = Isolation -> Concurent transactions do not interfere with each other
- D = Durability -> Commited data can't be undone even if the system fails

BASE:
- (BA) Basically Available. The systems guarantees availability
- (S) Soft State. Data might ve temporarily inconsistent or in flux (перетекать)
- (E) Eventually Consistent

CAP Theorem = choose consistency or availability


# Read-Through vs Write-Through Cache

1) Read Through Cache
- Read request -> check the cache first (if data available - cache hit)
- If the data is not in the cache (cache miss) -> read from primary store -> store in the cache -> return data to the client
- Subsequent read requests for the same data will be served directly from the cache until the data expires or is evicted.

Pros:
- Transparency: App only needs to interact with the cache, simplifying data access logic.
- Reduced Latency on Hits
- Reduces Load on Primary Storage

Cons:
- Cache Miss Penalty: 1st request is ont in the cache -> higer latency

2) Write-Through Cache
- Write request is made -> Data is first written to the cache
- Simultaneously(одновременно) the data is written to the primary storage
- Read requests can them be served from the cache, which contains the up-to-date data

Pros:
- Data Consistency: Provides strong consistency between the cache and the primary storage
- No Data Loss on Crach
- Simplified Writes: The application only interacts with the cache for write operations

Cons:
- Latency on Write Operations: Each write operation inclurs latency as it requires simultaneous writing to both the cache and the primary storage
- Higher Load on Primary Storage: Every write request impacts the primary storage

When to Use Each Strategy
Read-Through
- When read operations are frequent, data changes infrequently
- Tolerate eventual consistency for reads

Write-Through
- Suitable when data consistency is critical and you cannot afford stale data
- Necessary when the system requires immediate propagation of updates


# Batch Processing vs Stream Processing

1) Batch Processing - processing data in large, discrete blocks at scheduled intervals or after accumulating a certain amount of data
- Data is coollected over a period and processed all at once
- High Throughput: Efficent for processing large volumes of data when immediate action is not required
Ex: Payroll processing in a company.

Pros:
- Resource Efficent
- Simplicity

Cons:
- Delay in Insights
- Inflexibility


2) Stream Processing - processing data in real time as it arrives
- Immediate Processing
- Suitable for Real-Time Applications
Ex: Fraud detection in credit card transactions

Pros:
- Real-Time Analysis

Cons:
- Complexity
- Resource Intensive

# Load Balancer vs API Gateway

1) Load Balancer
- Primarily used to distribute network or application traffic across multiple servers.
- It accepts incoming requests and then routes them to one of several backend servers based on factors like the nb of current connections, server response time or server health.
- Different types of load balancers: hardware-based/software based.

2) API Gateway
- API management tool that sits between a client and a collection of back-end services. Acts as reverse proxy to route requests, simplify the API, and aggregate the results from various services.
- Can handle a variety of tasks, including request routing, API composition, rate limiting, authentication and authorization.
- Commonly used in microservices architectures to provide a unified interface to a set of microservices, making it easier for clients to consume the services.

Key Differences:
- Focus: Load balancers are focused on distributing traffic to prevent overloading servers and ensure high availability and redudancy. API Gateways are more avout providing a central point for managing, securing, and routing API calls.
- Functionality: Both can route request. The API Gateway offers more functioalities like API transformation, composition and security.

It's possible to use a load balancer and API gateway together.

# Proxy vs Reverse Proxy

1) Proxy (Forward Proxy) - intermediary for clients to interact with other servers.
- Privacy and Anonymity: hides the identity of the client from the internet servers they are accessing. Server sees the proxy's IP address, not the clients
- Content Filtering and Censorship:  Can be used to control and restroct access to specific websites or content
- Caching: May cache responses to reduce loading times and bandwidth usage for frequently asked resources

2) Reverse Proxy - intermediary for request from clients to one or more servers.
- Load Balancing: Distributes incoming requests.
- Security and Anonymity for Servers: Hides identities of the backend servers from the clients, providing an additional security layer.
- SSL Termination: Handles SSL encryption and decryption.
- Caching and Compression

Key Differences:
- Proxies are typically used for client privacy, internet access control and cahcing
- Reverse Proxies are used for server load balancing, security, performance and as an additional layer in the server architecture.

1) API Gateway - management tool that acts as a single entry point for a defined group of microservices.

- Handles authentification, authorization, rate limiting and logging
- Can translate between web protocols and backend protocols

- Typically used in microservices to  provide a unified interfeace to a set of independently deployable services.

2) Reverse Proxy - type of proxy that retrieves resources on behalf of a client from one or more servers.
- Load balancing
- Serurity
- Caching
- SSL Termination

Key Differences:
1) API Gateway
- primary facilitates and manages application-level traffic, acting as gatekeeper for microservces
- more complex in functionality, often providing additional features like request transformation, API orchestration, rate limiting
2) Reverse Proxy
- focusing on network-level concerns like load balancing, security, caching
- tend to be simplier and more focused on network and server efficency and security


# SQL vs NoSQL

1) SQL (Structured Query Language) Databases:
- Relational databases. Use structured query language (SQL) for defining and manipulationg data.
- Data stored in tables. Tables are related to each other
- Follow schema.

Key Features:
- ACID Compilamce: Ensures Reliable transactions
- Structured Data: Ideal for the data that fits well into tables
- Complex Queries: Powerful for complex queries and joining data from multiple tables

Ex: MySQL, PostgreSQL, Oracle, Microsoft SQL Server

Best for:
- Applications requiring complex transaxtions, like banking systems.
- When data structure won't change frequently

2) NoSQL Databases:
- Non-relational or distributed databases.

- Don't require a fixed schema, allowing the structure of the data to change over time
- Designed to scale out by using distributed clusters of hardware.

Key Features:
- Flexibility: Different types of data without fixed schema
- Scalability: Designed to scale out and hande very large amount of data
- Speed: Can be faster than SQL databases for certain queries, especially in big data and real-time web applications

Ex: MongoDB (Document), Redis (Key-Value), Cassandra (Wide-Column), Neo4j (Graph)

Best For:
- Systems needing to handle large amounts of diverse data
- Projects where the data structure can change over the time

SQL vs NoSQL - The difference
- Data Structure: Schema (SQL)/No schema (NoSQL)
- Scaling: SQL - vertically (more powerful hardware), NoSQL - horiontally (many servers)
- Transactions: SQL - robust transactions, NoSQL - limited transactions, but good speed ans scalability
- Complexity: SQL - complex queries, NoSQL - optimized for speed and simplicity of queries

Choosing Beween:
- SQL - when need ACID compilance (transactions), datastructure is clear and consistent
- NoSQL - when massive volumes of data or need flexibility in data model
